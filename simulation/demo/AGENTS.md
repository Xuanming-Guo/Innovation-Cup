# Demo-video work

This folder is the home for all ALTO demo-video work. These instructions
supplement [simulation/AGENTS.md](../AGENTS.md) and the [root AGENTS.md](../../AGENTS.md),
whose demo exception permits work here. Video work stays inside this folder; it does not
authorise running or changing the surrounding harness.

## Scope and file placement

- Use **ALTO** as the product name in narration, captions, window labels and new exports.
  Older source documents and archived captures may retain the previous name; preserve
  those originals and use ALTO in newly authored production material.
- Keep all video prompts, scripts, storyboards, narration, captions, captured or generated
  assets, editing code/projects, renders and production evidence under `simulation/demo/`.
- Use [the production prompt](demo-video-production-prompt.md) as the current five-minute
  brief. Create subfolders only as needed; do not duplicate this brief under `docs/`.
- Stage the entire video on one consistent desktop with ALTO open throughout.
  Teams call and conversation windows come forward when needed and then minimise or move
  aside. Keep desktop/window context visible in every scene; comparisons, employee-session
  captures, explanatory overlays and closing copy remain within that desktop presentation.
- Inspect the supplied [Teams call](references/microsoft-team-calls.png) and
  [Teams conversation](references/microsoft-teams-chats.png) references before creating those
  scenes. Preserve the original images. Calls and source conversations must use the referenced
  Microsoft Teams interfaces, with Teams' own styling; the conversation reference shows a
  channel's Posts view. Keep ALTO's interface visually separate.
- Relevant product sources and existing simulation documentation, fixtures and run artifacts
  may be read for grounding. Keep source artifacts and historical results unchanged.
- Video work does not authorise running or modifying the simulation harness, changing product
  behaviour, resetting tenants, contacting people, deploying or publishing. Follow any later
  explicit user authorisation for those actions.
- Scope searches and checks to this folder or specific reference files. Keep `simulation/`
  excluded from repository-wide commands.

## Product and evidence accuracy

- Recheck [implementation status](../../docs/implementation-status.md) and the supplied run
  evidence before making capability or performance claims. The production brief is not proof
  that the product or a connector works.
- Distinguish actual product footage, synthetic scenarios, authored replay, concept animation
  and live connectors. Preserve missing-result labels; never invent improvement percentages,
  baseline failures, solver traces or completed actions.
- Bind displayed metrics to their run, method, definition, units, denominator and source.
  Animate recorded graph changes; preserve identities and unchanged work.
- End the video with readable run statistics on the same desktop: focal-task elapsed time
  through acceptance, request-to-committed-and-communicated plan time, and distinct existing
  tasks changed. Reveal one metric at a time beside its relevant task, plan or graph, clearing
  the previous result. Apply this rule to earlier comparisons too; compare baseline/product
  values only for the same measure. Keep supporting counters and full tables in the evidence
  package, and retain only the last featured metric at the end. Keep new tasks, plan versions,
  owner changes and active effort distinct. Show timing endpoints and clock type; missing
  measurements remain explicit.
- Keep permissions, constraint validation, solver feasibility, independent schedule checks,
  approval, commitment, external delivery and work acceptance as separate claims.
- Use viewer-authorised content. Show factual action/evidence summaries rather than invented
  model thoughts. Required dependent work follows acceptance; accepted experience does not
  automatically grant skills or qualifications.

## Verification and handoff

- Check relative links after moving documents. For script edits, verify the timecodes still
  total the requested duration. For video edits, inspect the rendered output and captions.
- Report checks actually run and any missing footage, measurements or rendering capability.
  Do not run simulation tests merely to verify a video-document change.
- Keep editable sources and exported deliverables here, and link the final files in the handoff.
